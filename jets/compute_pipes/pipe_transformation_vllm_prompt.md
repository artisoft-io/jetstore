# VllmTransformationPipe — prompt configuration

How a prompt is configured for a vLLM server and what the operator actually puts on the wire.

Companion to [`pipe_transformation_vllm_design.md`](pipe_transformation_vllm_design.md), which covers
the backend as a whole, and to
[`pipe_transformation_infer_readme.md`](pipe_transformation_infer_readme.md), which covers the shared
plumbing. This file covers one thing: the prompt — where it is declared, how it reaches the request,
and the exact JSON that reaches vLLM.

Implementation: `pipe_transformation_vllm.go` (`vllmRequestBase`, `vllmStructuredOutput`,
`BuildRequest`); the templating itself is `pipe_transformation_infer.go`. Configuration types:
`PromptTemplateSpec`, `VllmSpec`, `InferCommonSpec` (`pipes_model.go`).

**Every payload below was generated by running the operator's own code** —
`applyVllmDefaults`, `vllmRequestBase`, `vllmStructuredOutput` and `vllmBackend.BuildRequest` —
against the configuration shown next to it. So were the error messages in §5. They are indented here
for readability; the body actually POSTed is compact.

The config fragments show only the prompt-relevant keys. A working `vllm_config` also needs
`output_mapping`, an `output_channel` sharing the input channel's `channel_spec_name`, and usually an
`error_channel` — see the design doc.

---

## 1. Where a prompt is declared

**Shared, and stated once in the infer readme §2.3**: inline `prompt_template` on `vllm_config`, or
`prompt_template_name` into the top-level `prompt_templates` registry — exactly one of the two, and a
named template's `system_prompt` and `response_format` are defaults the operator's own values beat.

**One consequence is this backend's own.** Because a named template's `response_format` is adopted
during the build, and because this backend translates `response_format` **once** rather than per
request, it implements `inferBackendPreparer` so the translation runs after the adoption — design doc
§6. It decides whether the request below carries a guided-decoding field at all.

## 2. The two kinds of placeholder

**Shared, and stated once in the infer readme §2.4**: `$VAR` and `${VAR}` from the cpipes env,
resolved at build time; `{{column_name}}` and `{{@record}}` compiled at build time and rendered per
record. A `{{col}}` naming no column is a build-time error, and only `{{` opens a placeholder — so a
JSON skeleton can be written into a template as-is.

Nothing about the templating differs between the backends. What differs is where the rendered string
lands, which is §3.

## 3. Where the prompt lands in the request

**This is the part that is not shared**, and it depends on `api`.

| `api` | Route | The prompt becomes | `system_prompt` |
|---|---|---|---|
| `chat` *(default)* | `/v1/chat/completions` | `messages[].role: "user"` | `messages[].role: "system"`, first |
| `completions` | `/v1/completions` | `prompt`, a bare string | **build-time error** |

`/v1/completions` has no message roles, so a system prompt has nowhere to go. Folding it into the
prompt would silently reinterpret what the author wrote.

**`stream` is always `false`** — the operator needs the complete response before it can map it.

## 4. Examples

### Example 1 — the minimum

```json
{
  "type": "vllm",
  "vllm_config": {
    "model": "granite4.1:3b",
    "prompt_template": "Classify the claim below.\nDiagnosis: {{diagnosis}}\n"
  }
}
```

POST `/v1/chat/completions`:

```json
{
  "messages": [
    {
      "role": "user",
      "content": "Classify the claim below.\nDiagnosis: tooth ache, lower left molar\n"
    }
  ],
  "model": "granite4.1:3b",
  "stream": false
}
```

No guided-decoding field, and **`constrained` is false** — which is what makes a `finish_reason` of
`length` an ordinary truncation here rather than a row-level error (design doc §4).

### Example 2 — `response_format: "json"` is json mode

```json
{
  "vllm_config": {
    "model": "granite4.1:3b",
    "response_format": "json",
    "prompt_template": "Classify the claim below.\nReturn JSON: {\"category\": <string>}\nDiagnosis: {{diagnosis}}\n"
  }
}
```

```json
{
  "messages": [
    {
      "role": "user",
      "content": "Classify the claim below.\nReturn JSON: {\"category\": <string>}\nDiagnosis: tooth ache\n"
    }
  ],
  "model": "granite4.1:3b",
  "response_format": {
    "type": "json_object"
  },
  "stream": false
}
```

The string `"json"` — ollama's spelling — becomes OpenAI json mode. **`constrained` is true**, so a
truncated response is now a reported error rather than a parse failure.

`<` came out as `<` because Go's `encoding/json` escapes `<`, `>` and `&` by default. That is a
JSON string escape, not a change to the prompt; the server's decoder turns it back before the model
sees it. Worth recognising, because it makes a debug dump look mangled when nothing is wrong.

### Example 3 — a schema, on the default `json_schema` arm

```json
{
  "vllm_config": {
    "model": "granite4.1:3b",
    "system_prompt": "You are a claims classification assistant.",
    "prompt_template": "Diagnosis: {{diagnosis}}\n",
    "response_format": {
      "type": "object",
      "properties": {
        "category":   { "type": "string" },
        "confidence": { "type": "number" }
      },
      "required": ["category", "confidence"]
    }
  }
}
```

```json
{
  "messages": [
    {
      "role": "system",
      "content": "You are a claims classification assistant."
    },
    {
      "role": "user",
      "content": "Diagnosis: tooth ache, lower left molar\n"
    }
  ],
  "model": "granite4.1:3b",
  "response_format": {
    "json_schema": {
      "name": "response",
      "schema": {
        "properties": {
          "category":   { "type": "string" },
          "confidence": { "type": "number" }
        },
        "required": ["category", "confidence"],
        "type": "object"
      },
      "strict": true
    },
    "type": "json_schema"
  },
  "stream": false
}
```

**The schema is the one the author wrote, wrapped and not rewritten.** `name` is the constant
`response` because the OpenAI shape requires one and nothing reads it back; `strict: true` is what
makes this the equivalent of `guided_json` rather than a hint.

**This is the same `response_format` an `ollama_config` would carry**, which is the point: a
`.pc.json` moves between the backends by changing the type token, not the schema.

### Example 4 — the same schema on the `guided_json` arm

```json
{
  "vllm_config": {
    "model": "granite4.1:3b",
    "structured_output": "guided_json",
    "response_format": { "…": "as above" }
  }
}
```

```json
{
  "guided_json": {
    "properties": {
      "category":   { "type": "string" },
      "confidence": { "type": "number" }
    },
    "required": ["category", "confidence"],
    "type": "object"
  },
  "messages": [
    {
      "role": "user",
      "content": "Diagnosis: tooth ache, lower left molar\n"
    }
  ],
  "model": "granite4.1:3b",
  "stream": false
}
```

**Do not reach for this arm without a reason.** Against the pinned vLLM v0.28.0 this field is
accepted and discarded — 0 of 24 conformant against 23 of 24 for example 3 — and the server says
nothing. See the design doc §3.

### Example 5 — `options` is merged at the top level

```json
{
  "vllm_config": {
    "model": "granite4.1:3b",
    "system_prompt": "You are a claims classification assistant.",
    "options": { "temperature": 0, "seed": 42, "max_tokens": 512, "top_p": 0.9 },
    "response_format": { "…": "the schema of example 3" }
  }
}
```

```json
{
  "max_tokens": 512,
  "messages": [
    { "role": "system", "content": "You are a claims classification assistant." },
    { "role": "user",   "content": "Diagnosis: tooth ache\n" }
  ],
  "model": "granite4.1:3b",
  "response_format": { "…": "as example 3" },
  "seed": 42,
  "stream": false,
  "temperature": 0,
  "top_p": 0.9
}
```

**`temperature`, `seed`, `max_tokens` and `top_p` are peers of `model`, not members of an `options`
object.** That is the OpenAI api's shape. An `ollama_config` with the same four keys nests them under
`options` on the wire — so this is one of the few places where a document really does mean something
different to the two backends, and it is handled by the operator rather than by the author.

### Example 6 — the completions api

```json
{
  "vllm_config": {
    "model": "granite4.1:3b",
    "api": "completions",
    "options": { "temperature": 0, "max_tokens": 256 },
    "prompt_template": "Classify the claim below.\nDiagnosis: {{diagnosis}}\n"
  }
}
```

POST `/v1/completions`:

```json
{
  "max_tokens": 256,
  "model": "granite4.1:3b",
  "prompt": "Classify the claim below.\nDiagnosis: tooth ache\n",
  "stream": false,
  "temperature": 0
}
```

`messages` is gone and `prompt` is a bare string. Adding `system_prompt` to this config fails the
build rather than changing the route.

## 5. Build-time errors

Quoted from the operator, not paraphrased.

**A reserved key in `options`:**

```
error: vllm_config options cannot set 'model', the operator sets it itself (reserved: model,
stream, messages, prompt, guided_json, response_format). Sampling parameters such as
temperature, max_tokens and top_p are what options is for
```

**A `response_format` string that is not `"json"`:**

```
error: vllm_config response_format 'yaml' is not understood, expecting the string "json" or a
json schema document
```

**A `response_format` that is neither a string nor an object:**

```
error: vllm_config response_format must be the string "json" or a json schema document, got [1,2]
```

**An unknown `structured_output`:**

```
error: unknown vllm_config structured_output 'outlines', expecting 'guided_json' or 'json_schema'
```

**A system prompt on the completions api:**

```
error: vllm_config system_prompt requires api 'chat': the 'completions' api has no system message
```

All of these are raised **before any GPU time is spent**, which is the reason the request base is
built once at build time rather than per record.

## 6. Seeing the rendered prompt

`is_debug: true` logs the prompt and the response per row. It is the shared plumbing's flag and
behaves as it does for ollama.

For the request body as sent, note that `vllmRequestBase` runs once — so a single logged body is
representative of every row except for the `messages`/`prompt` content.

## 7. What this operator does not have

`keep_alive` and `think` are `ollama_config` keys with no OpenAI equivalent. A document that carries
them against the vLLM backend is **not refused** — the `infer` operator logs that the key is inert on
this backend, because a document written to serve both backends is expected to carry both operators'
specialized keys. See the infer readme.

There is no equivalent of the Infer Server Admin screen's request envelope for vLLM: that screen
talks to the Ollama infer service.
