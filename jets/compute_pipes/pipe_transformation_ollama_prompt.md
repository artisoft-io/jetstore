# OllamaTransformationPipe — the wire payloads

What the ollama backend actually puts on the wire, by worked example.

Companion to [`pipe_transformation_ollama_design.md`](pipe_transformation_ollama_design.md), which
covers the backend as a whole, and to
[`pipe_transformation_infer_readme.md`](pipe_transformation_infer_readme.md), which covers
everything shared.

**The rules are not here.** Where a prompt is declared, how the two kinds of placeholder resolve, what
a build-time error looks like and how to see a rendered prompt are all shared by `ollama`, `vllm` and
`embed` — infer readme §2.3, §2.4, §2.9 and §2.10. **This file is the payloads**, because a payload is
the one thing that really is this backend's own.

Implementation: `pipe_transformation_ollama.go` (`BuildRequest`); the templating is
`pipe_transformation_infer.go`. Configuration types: `PromptTemplateSpec`, `OllamaSpec`,
`InferCommonSpec` (`pipes_model.go`).

**Every payload below was generated by running the operator's own code** — `resolveInferTemplate`,
`utils.ReplaceEnvVars`, `compileInferPromptTemplate`, `render` and the backend's `BuildRequest` —
against the configuration shown next to it. They are indented here for readability; the body actually
POSTed is compact.

The config fragments show only the prompt-relevant keys. A working `ollama_config` also needs
`output_mapping`, an `output_channel` sharing the input channel's `channel_spec_name`, and usually an
`error_channel`.

> *This file was a full prompt-configuration document until 2026-09-10, written 2026-08-05 — before
> the shared plumbing was extracted on 2026-08-16. The rules it stated are now stated once, in the
> infer readme, and the payloads stayed here. Nothing about them changed; three of the four functions
> that produce them were renamed `ollama*` → `infer*` at the extraction.*

## 1. Where the prompt lands in the request

| Config key | `/api/generate` | `/api/chat` |
|---|---|---|
| rendered prompt | `prompt` | `messages[]`, `role: "user"` |
| `system_prompt` | `system` (omitted when empty) | `messages[0]`, `role: "system"` (omitted when empty) |
| `response_format` | `format` | `format` |
| `options` | `options`, **nested** | `options`, **nested** |
| `keep_alive` | `keep_alive` | `keep_alive` |
| `think` | `think` | `think` |
| — | `stream: false`, always | `stream: false`, always |

`keep_alive` defaults to `30m` and so appears in every payload below; it must carry a unit, since a
bare integer is read as seconds.

**Contrast with vLLM**, where sampling parameters are merged at the **top level** and a system prompt
is only legal on the chat api —
[`pipe_transformation_vllm_prompt.md`](pipe_transformation_vllm_prompt.md) §3.

## 2. The payloads

Examples 1–6 and 8 share this input channel and record:

| Column | `claim_id` | `diagnosis` | `procedure_code` | `claim_category` | `claim_confidence` | `infer_tokens` |
|---|---|---|---|---|---|---|
| Value | `c-8837` | `tooth ache, lower left molar` | `D2740` | *null* | *null* | *null* |

The last three columns are the ones the model fills — they exist in the shared channel spec and are
null when the prompt is rendered.

### Example 1 — inline template, column placeholders

The minimal prompt configuration: an inline template and JSON mode.

```json
{
  "type": "ollama",
  "ollama_config": {
    "model": "granite4.1:3b",
    "prompt_template": "Classify the claim below.\nReturn JSON: {\"category\": <string>, \"confidence\": <0..1>}\n\nDiagnosis: {{diagnosis}}\nProcedure: {{procedure_code}}\n",
    "response_format": "json"
  }
}
```

POST `/api/generate`:

```json
{
  "model": "granite4.1:3b",
  "prompt": "Classify the claim below.\nReturn JSON: {\"category\": \u003cstring\u003e, \"confidence\": \u003c0..1\u003e}\n\nDiagnosis: tooth ache, lower left molar\nProcedure: D2740\n",
  "stream": false,
  "format": "json",
  "keep_alive": "30m"
}
```

Two things to read off this payload. The literal braces of the `{"category": ...}` example in the
prompt text are **not** placeholders — only `{{` opens one — so a JSON skeleton can be written into a
template as-is. And `<` came out as `\u003c`: Go's `encoding/json` escapes `<`, `>` and `&` by
default. That is a JSON string escape, not a change to the prompt — Ollama's decoder turns it back
into `<` before the model sees it. It is worth recognising, because it makes a debug dump of the
request body look mangled when nothing is wrong.

### Example 2 — named template, system prompt and a JSON schema

Moving the same prompt into `prompt_templates` lets several steps share it, and lets the schema
travel with the prompt text rather than with each operator.

```json
{
  "prompt_templates": [
    {
      "key": "classify_claim",
      "template": "Diagnosis: {{diagnosis}}\nProcedure: {{procedure_code}}\n",
      "system_prompt": "You are a claims classification assistant. Answer with JSON only.",
      "response_format": {
        "type": "object",
        "properties": {
          "category": {"type": "string"},
          "confidence": {"type": "number"}
        },
        "required": ["category", "confidence"]
      }
    }
  ],
  "pipes_config": [
    {
      "type": "ollama",
      "ollama_config": {
        "model": "granite4.1:3b",
        "prompt_template_name": "classify_claim"
      }
    }
  ]
}
```

POST `/api/generate`:

```json
{
  "model": "granite4.1:3b",
  "prompt": "Diagnosis: tooth ache, lower left molar\nProcedure: D2740\n",
  "system": "You are a claims classification assistant. Answer with JSON only.",
  "stream": false,
  "format": {
    "type": "object",
    "properties": {
      "category": {"type": "string"},
      "confidence": {"type": "number"}
    },
    "required": ["category", "confidence"]
  },
  "keep_alive": "30m"
}
```

`response_format` is raw passthrough: `"json"` and a full JSON schema are both valid, and the schema
is forwarded byte for byte. Structured output is what makes `output_mapping`'s dot-notation paths
(`category`, `confidence`) reliable.

### Example 3 — the operator overrides the template's defaults

Same named template (with `"response_format": "json"` this time), one operator specialising it:

```json
{
  "type": "ollama",
  "ollama_config": {
    "model": "granite4.1:3b",
    "prompt_template_name": "classify_claim",
    "system_prompt": "You are a dental claims auditor. Answer with JSON only."
  }
}
```

POST `/api/generate`:

```json
{
  "model": "granite4.1:3b",
  "prompt": "Diagnosis: tooth ache, lower left molar\nProcedure: D2740\n",
  "system": "You are a dental claims auditor. Answer with JSON only.",
  "stream": false,
  "format": "json",
  "keep_alive": "30m"
}
```

The operator's `system_prompt` won; `response_format` fell back to the template's, since the operator
did not set it. The two settings are independent — overriding one does not discard the other.

### Example 4 — env var placeholders, both syntaxes

With this `context` section, and `$SESSIONID` / `$PROCESS_NAME` supplied by the framework:

```json
{
  "context": [
    {"type": "value", "key": "$CLIENT", "expr": "acme_health"},
    {"type": "file_key_component", "key": "${FILE_YEAR}", "expr": "year"}
  ],
  "pipes_config": [
    {
      "type": "ollama",
      "ollama_config": {
        "model": "granite4.1:3b",
        "prompt_template": "Client: $CLIENT\nFile year: ${FILE_YEAR}\nSession: $SESSIONID\n\nClassify claim {{claim_id}} with diagnosis: {{diagnosis}}\n",
        "system_prompt": "You are classifying claims for $CLIENT, process $PROCESS_NAME."
      }
    }
  ]
}
```

For the run where `$SESSIONID` is `20260805143000`, `$PROCESS_NAME` is `claimsClassification` and the
input file key puts `${FILE_YEAR}` at `2026`, POST `/api/generate`:

```json
{
  "model": "granite4.1:3b",
  "prompt": "Client: acme_health\nFile year: 2026\nSession: 20260805143000\n\nClassify claim c-8837 with diagnosis: tooth ache, lower left molar\n",
  "system": "You are classifying claims for acme_health, process claimsClassification.",
  "stream": false,
  "keep_alive": "30m"
}
```

Both placeholder kinds in one template, resolved at different times: `$CLIENT`, `${FILE_YEAR}` and
`$SESSIONID` were substituted once when the node was built and are identical in every record's
prompt; `{{claim_id}}` and `{{diagnosis}}` were rendered for this record. Non-string env values are
formatted on substitution — a `file_key_component` of `year` is an `int` in the env and lands as
`2026`.

Note also that `$CLIENT` was substituted in the system prompt, and that no `format` field is present:
`response_format` was not configured, so the operator does not send one.

### Example 5 — the whole record, plus options

`{{@record}}` is the reserved placeholder for the entire record as a JSON object — usually the most
convenient shape when the prompt is about the row rather than about two named fields.

```json
{
  "type": "ollama",
  "ollama_config": {
    "model": "granite4.1:3b",
    "prompt_template": "Summarize this claim record as JSON:\n{{@record}}\n",
    "response_format": "json",
    "options": {"temperature": 0, "num_ctx": 8192},
    "keep_alive": "60m"
  }
}
```

POST `/api/generate`:

```json
{
  "model": "granite4.1:3b",
  "prompt": "Summarize this claim record as JSON:\n{\"claim_category\":null,\"claim_confidence\":null,\"claim_id\":\"c-8837\",\"diagnosis\":\"tooth ache, lower left molar\",\"infer_tokens\":null,\"procedure_code\":\"D2740\"}\n",
  "stream": false,
  "format": "json",
  "options": {"num_ctx": 8192, "temperature": 0},
  "keep_alive": "60m"
}
```

Two properties of `{{@record}}` worth knowing before using it:

- **It emits every column of the channel spec, including the ones the model is meant to fill.** They
  are null at render time (`claim_category`, `claim_confidence`, `infer_tokens` above). If their
  presence confuses the model, name the input columns explicitly instead.
- **The keys come out alphabetically sorted**, not in channel order — it is marshalled from a map.

`options` is raw passthrough to Ollama (`temperature`, `num_ctx`, `seed`, `num_predict`…). Keep
`num_ctx` within the server's `OLLAMA_CONTEXT_LENGTH` budget; see `infer_server_readme.md` for what
the KV cache costs.

### Example 6 — chat API

```json
{
  "type": "ollama",
  "ollama_config": {
    "model": "granite4.1:3b",
    "api": "chat",
    "prompt_template": "Diagnosis: {{diagnosis}}\nProcedure: {{procedure_code}}\n",
    "system_prompt": "You are a claims classification assistant.",
    "think": true
  }
}
```

POST `/api/chat`:

```json
{
  "model": "granite4.1:3b",
  "messages": [
    {"role": "system", "content": "You are a claims classification assistant."},
    {"role": "user", "content": "Diagnosis: tooth ache, lower left molar\nProcedure: D2740\n"}
  ],
  "stream": false,
  "keep_alive": "30m",
  "think": true
}
```

The prompt configuration is identical to the generate case — same template, same placeholders. Only
the envelope changes: `system_prompt` becomes the first message instead of a `system` field, and the
rendered prompt becomes the user message. There is no conversation history; every record is a fresh
single-turn exchange.

With `think: true` the reasoning text comes back separately and is reachable from
`output_mapping` via `"source": "thinking"`.

### Example 7 — a short record and null values

Records shorter than the channel's column count are legitimate here (see `pad_short_rows_with_nulls`).
This template, rendered against the one-value record `["c-9001"]`:

```json
{
  "type": "ollama",
  "ollama_config": {
    "model": "granite4.1:3b",
    "prompt_template": "Claim [{{claim_id}}] diagnosis [{{diagnosis}}] record {{@record}}\n"
  }
}
```

POST `/api/generate`:

```json
{
  "model": "granite4.1:3b",
  "prompt": "Claim [c-9001] diagnosis [] record {\"claim_category\":null,\"claim_confidence\":null,\"claim_id\":\"c-9001\",\"diagnosis\":null,\"infer_tokens\":null,\"procedure_code\":null}\n",
  "stream": false,
  "keep_alive": "30m"
}
```

A missing or null value renders as the empty string rather than failing the record — and as `null`
inside `{{@record}}`. A prompt that must distinguish "absent" from "empty" has to say so in its text;
the renderer will not do it for you.

Values are stringified as: `nil` → empty, `string` as-is, `[]byte` → string, `sql.NullString` → its
value or empty, anything else via `%v`.

### Example 8 — whitespace in a placeholder

```json
{
  "type": "ollama",
  "ollama_config": {
    "model": "granite4.1:3b",
    "prompt_template": "Diagnosis: {{ diagnosis }}"
  }
}
```

POST `/api/generate`:

```json
{
  "model": "granite4.1:3b",
  "prompt": "Diagnosis: tooth ache, lower left molar",
  "stream": false,
  "keep_alive": "30m"
}
```

The name is trimmed inside the braces; the surrounding literal text is not touched.

## 3. The other request surface: the Infer Server Admin screen

**Workspace IDE → Infer Server Admin** is a console over the same infer server, reached through the
apiserver's `/inferServer` endpoint rather than through a pipeline. Its **Request** box takes a
different kind of JSON from everything above, so it is worth being explicit about what goes in it.

Implementation: `jets/apiserver/api_infer_server.go`,
`jetsclient/lib/modules/workspace_ide/infer_server_admin/`. Operational context — starting and
stopping the GPU instance, what it costs — is in `infer_server_readme.md`.

### What goes in the Request box

A complete **request envelope**: an `action` naming what to do, and a `body` that is the Ollama
request for that action.

```json
{
  "action": "pull_model",
  "body": {
    "model": "granite4.1:3b",
    "stream": false
  }
}
```

Submit parses the box as JSON (a syntax error is reported in the Response box, nothing is sent) and
POSTs it to `/inferServer`. The four macro buttons above the box — List Models, Pull Model, Show
Model, Delete Model — fill it with a ready-to-submit envelope for each proxied action, so the usual
flow is click, edit the model tag, Submit.

The apiserver looks the action up in a closed allow list and supplies the method and route itself.
For the envelope above it sends, to `<JETS_INFER_URL>/api/pull` with
`Content-Type: application/json`:

```json
{
    "model": "granite4.1:3b",
    "stream": false
  }
```

That is the `body` **forwarded byte for byte** — it is held as a `json.RawMessage` and never
re-encoded, which is why the odd indentation of the typed envelope survives into the request. Only
`body` is sent; `action` is consumed by the apiserver and never reaches Ollama.

The answer comes back in the Response box wrapped in the HTTP status Ollama replied with:

```json
{
  "statusCode": 200,
  "response": {"status": "success"}
}
```

`response` is Ollama's own answer, parsed when it is JSON and passed through as text when it is not —
an Ollama error is reported here rather than collapsed into an apiserver failure, since its errors
are as useful as its successes.

### Accepted values for `action`

Seven, and no others. The client names an action, never a path: a caller-supplied path would make the
apiserver an open proxy to anything reachable inside the VPC.

| `action` | What it does | `body` |
|---|---|---|
| `server_status` | `awsi.GetInferServerStatus` — running / stopped / starting / stopping | ignored |
| `start_server` | `awsi.StartInferServer` (ASG capacity, then the ECS task), then re-reads the status | ignored |
| `stop_server` | `awsi.StopInferServer`, then re-reads the status | ignored |
| `list_models` | `GET /api/ps` — the loaded models and their VRAM residency | forwarded |
| `pull_model` | `POST /api/pull` | forwarded |
| `show_model` | `POST /api/show` | forwarded |
| `delete_model` | `DELETE /api/delete` | forwarded |

The first three are lifecycle actions handled entirely in AWS; they never call Ollama and their
`body` may be omitted. `server_status` answers `{"status": {…}}`; `start_server` and `stop_server`
answer `{"changed": …, "status": {…}}`, where `changed: false` means the server was already in the
requested state — a successful no-op, not a failure. The last four are proxied and answer with the
`statusCode` / `response` wrapper shown above. The buttons on the screen cover the lifecycle actions,
but typing one into the box works too, and the screen picks the status up from the answer either way.

Four things that bite:

- **`"stream": false` on `pull_model`.** Ollama otherwise streams NDJSON progress, which the screen
  cannot render.
- **An unknown action is a 422** naming the seven accepted values — not a 404, and nothing is sent.
- **A missing `JETS_INFER_URL` is a 503** saying the infer server is not part of this deployment.
  That is deliberately distinct from a connection failure, which reports the server as possibly
  stopped: one is a deploy-time choice, the other is a button away.
- **Every action needs the `infer_server_admin` capability**, checked in the apiserver. The disabled
  menu entry is presentation; the endpoint is the enforcement point.

### This screen cannot send a prompt

The allow list has no `/api/generate` or `/api/chat` entry, by design — this endpoint administers
models, it does not run inference. Prompt configuration is the operator's business — this file's §1
and §2, and the rules in the infer readme §2.3 and §2.4. To exercise a prompt by hand, call the infer
server directly with a chat request; the
`infer_server_readme.md` verification section does exactly that, from
`data/unit_test_data/cintel/ollama_unit_test_chat.json` in the `jets_ws` workspace.
