What a compile does around the rules themselves, from `jets/workspace`: what it needs to run, what it
rebuilds, and where it sits in the apiserver's start. How the rules are compiled is
in [The JetRules compiler](/docs/developer/engine/compiler/).

## Compiling validates the flow documents first, and needs node to do it

*2026-10-01.*

**Symptom.** A compile that used to succeed fails before any rule is compiled, with
`workspace asset validation failed: cannot run the validator: node is not on PATH` or
`jets_validate_workspace.mjs is not beside <executable>` -- typically an apiserver started
on a workstation, or a binary run outside the images.

**Cause.** `CompileWorkspace` now runs `node jets_validate_workspace.mjs <workspace>` over
`user_flows/` and `table_configs/` before compiling (`validateWorkspaceAssets`,
`asset_validation.go`), and **fails rather than skips when it cannot run it**. That is
deliberate: these documents will be generated by a model, the cross-document checks exist
only in TypeScript, and a validator that skips itself where node is absent would pass every
compile in an image without node and look exactly like a pass.

**Where it looks.** Node: `JETS_NODE`, else `node` on `PATH`. The script:
`JETS_WORKSPACE_VALIDATOR`, else `jets_validate_workspace.mjs` beside the running executable
-- which is where the images put it (`/usr/local/bin` beside the apiserver and
`run_reports`, `/app` beside `compile_workspace`). Neither has a fallback beyond that.

**On a workstation**, build the script once and point at it:

```bash
cd jetsclient_ide && npm ci && npm run build:validator
export JETS_WORKSPACE_VALIDATOR=$PWD/dist-validator/jets_validate_workspace.mjs
```

**The one caller that does not validate is `run_reports`**, which passes
`SkipAssetValidation` with its reason: it recompiles to rebuild lookup tables and changes
no flow document, and the `cpipes` image it runs in carries no node. The skip is logged and
written into the compile log; an opt-out with an empty reason fails the compile instead.

**Exit statuses are the contract.** 0 is a pass (warnings print and do not fail), 1 is an
invalid document, and anything else -- 2 for a directory the script could not read, a
signal, the two-minute timeout -- is reported as a validator that did not finish. Run the
script by hand over a workspace to see the findings with file and JSON Pointer; `--json`
prints them as data.

## `lookup.db` is rebuilt only when what it is built from changed

Packaging `lookup.db` was most of a compile — about 2.2 s of 2.5 s on `jets_ws`,
measured 2026-10-11 — and a compile now blocks rules unit tests, so it is time a
user waits. `EnsureLookupDb` (`lookup_db_fingerprint.go`) skips it when the
existing file carries a SHA-256 of exactly the inputs a rebuild would read: the
deduplicated lookup definitions, the bytes of every CSV they name, the SQLite
library version and `lookupDbFormatVersion`. The compile log says which happened:

```
Lookup tables packaged into lookup.db in 2.153s (no lookup.db; inputs sha256 35f52110dd4a)
lookup.db is up to date, packaging skipped in 14ms (inputs sha256 35f52110dd4a unchanged)
```

Three things the code cannot tell you:

- **Modification times are not consulted**, on purpose: a git checkout, a Docker
  `COPY` and the database sync all rewrite them. Touching a CSV does not rebuild;
  changing one byte does.
- **Bump `lookupDbFormatVersion` when you change what the packager writes** —
  `lookup_tables.go`, or what it calls (`jets/csv`, `rdf.ParseBool`). Code cannot
  fingerprint itself, so that one input is a convention.
- **A rebuild writes a new file and renames it into place.** It used to drop and
  recreate each table inside the old file, so a lookup removed from the rules
  stayed in `lookup.db` indefinitely, and a rebuild did not produce the bytes a
  fresh build does. A skipped `lookup.db` is now byte-for-byte what a rebuild would
  write, which is what makes skipping safe to reason about, and a failed build
  leaves the previous file intact. Anything else — no file, an unreadable or
  truncated one, one built before the fingerprint existed — rebuilds, so a fresh
  container always builds.


## The compile sits between two halves of a schema migration, and the order is load-bearing

**Symptom.** The apiserver fails to start against a database whose schema predates the
release, five lines into the compile:

```
Compiling workspace jets_ws at version 1788587129
Result from git rev-parse HEAD :: 3a157e86…
Updating workspace version in database to 1788587129 for workspace jets_ws
error while compiling workspace: while inserting workspace version into
 workspace_version table: ERROR: column "workspace_name" of relation
 "workspace_version" does not exist (SQLSTATE 42703)
Failed to start apiserver: failed to start command: exit status 1
```

**Cause.** `listenAndServe` ran three checks in order: `checkJetStoreSchema`, then
`checkWorkspaceVersion`, then `checkDomainTablesVersion`. The first only acts when
`jetstore_release` does **not** exist, so on an existing database it is a no-op. The
third is where the migration lived. So the second wrote columns the third was
responsible for adding.

**Why the migration was last, and why only half of it had to be.** Domain tables are
generated from the workspace's classes, which are known only after the compile — so
that half genuinely cannot move. **The system tables are not**: they come from
`jets/jets_schema.json`, which is in the image. Splitting the two is the fix:
`checkSystemTablesVersion` now runs before the compile, on the same release gate, and
`checkDomainTablesVersion` keeps the domain half.

### `update_db` could not simply be run earlier, and that is worth knowing before trying

**The process reads `$WORKSPACES_HOME/$WORKSPACE/build/tables.json` unconditionally at
the end of `doJob`** — a file `compileWorkspaceV2` writes and every workspace
`.gitignore` excludes. There is no flag combination that makes `update_db` safe to run
before a compile; it aborts at *"while reading table.json json file"*. That is why the
migration was extracted into `jets/migratedb` and called as a function rather than the
binary being invoked earlier.

### The gate is a string comparison, and the version table is append-only

`checkDomainTablesVersion` reads `SELECT MAX(version) FROM jetsapi.jetstore_release`
and fires on `jetstoreVersion > version.String` — **a string comparison of what are
usually timestamps**. Equal-length values compare correctly; a shorter one would not.

**`jetstore_release` is an append log**: `addVersionToDb` only ever `INSERT`s. A
deployment we examined held 165 rows. **Reading it with anything other than `MAX` gives
an arbitrary answer** — a bare `SELECT version` returned a value five releases stale
while `MAX(version)` returned the current one, from the same table at the same moment.
Anyone querying this table by hand should use the query the code uses.

**On a release upgrade the version is deliberately not recorded** — the branch ends
`// DO NOT UPDATE version in database, hence return here`. So the migration re-runs on
the next start until something else records it, which is why both migration paths must
be idempotent rather than merely correct.
