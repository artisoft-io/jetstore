Compute Pipes operator that calls an Ollama server once per input record and augments that
record in place with values extracted from the model's response.

Implementation: `pipe_transformation_ollama.go`, transformation type `ollama`, configuration
`ollama_config` (`OllamaSpec`).

**This document covers the backend only** — the Ollama request and response shapes, the keys
that are this server's own, and the failure modes that are its own.

**Everything else is shared** and lives in
[the inference operators page](/docs/developer/compute-pipes/operators/infer/): the operator
shell, the worker pool, the prompt template, the response mapping, the retry policy, the
circuit breaker, the cost guard, `on_error`, the channel rules and the whole of
`InferCommonSpec`. It is one implementation in `pipe_transformation_infer.go`, reached
through the `inferBackend` seam, and `ollama`, `vllm` and `embed` all use it.

**Most documents should not name this operator at all.** `type: infer` with
`infer_config.backend` resolves to `ollama` or `vllm` at startup, which is what lets one
document serve both.

## 1. Configuration — the keys that are this backend's

Every other key of `ollama_config` is `InferCommonSpec`, embedded anonymously so field
promotion leaves the wire shape flat. See the [the inference operators page, §2.2](/docs/developer/compute-pipes/operators/infer/#22-configuration--infercommonspec).

| Key | Default | Meaning |
|---|---|---|
| `model` | *required* | Ollama model tag, e.g. `granite4.1:3b` |
| `api` | `generate` | `generate` → `/api/generate`, `chat` → `/api/chat` |
| `options` | — | Ollama `options`: `temperature`, `num_ctx`, `seed`, `num_predict`… **nested**, raw passthrough |
| `keep_alive` | `30m` | Keeps the model resident between rows — **the single most important throughput setting** |
| `think` | — | Reasoning models |
| `server.url`, `server.headers` | — | [the inference operators page, §2.8](/docs/developer/compute-pipes/operators/infer/#28-url-resolution) |

**`keep_alive` must carry a unit**; a bare integer is read as seconds. It appears in every
payload because it is defaulted rather than omitted.

**`options` is nested here and top-level on vLLM.** That is the difference between the two
servers' APIs, not a choice — the vLLM operator merges the same map into the request body
because the OpenAI shape makes sampling parameters peers of `model`.

**`response_format` is shared configuration with an unshared meaning.** Ollama takes it as
`format` and treats it as **best effort**; vLLM constrains the decoder. Measured
2026-09-09: ollama's `format` does reach the model and does constrain decoding — the
schema-in-the-prompt workaround some code once carried rests on a premise that is false.

## 2. What is sent

One POST per record to `<server url>/api/generate` (default) or `<server url>/api/chat`,
`Content-Type: application/json` plus any `server.headers`.

| Config key | `generate` field | `chat` field |
|---|---|---|
| `model` | `model` | `model` |
| rendered prompt | `prompt` | `messages[]`, `role: "user"` |
| `system_prompt` | `system` (omitted when empty) | `messages[0]`, `role: "system"` (omitted when empty) |
| `response_format` | `format` | `format` |
| `options` | `options` | `options` |
| `keep_alive` | `keep_alive` | `keep_alive` |
| `think` | `think` | `think` |
| — | `stream: false`, always | `stream: false`, always |

**`stream` is never configurable**: the operator needs the complete response before it can
map it onto the record.

**Unlike the vLLM backend, a `system_prompt` is legal on both APIs** — `/api/generate` has a
`system` field of its own, so nothing has to be folded into the prompt.

See [Ollama wire payloads](/docs/developer/compute-pipes/operators/infer-ollama-payloads/) for the
exact bodies, generated by running the operator's own code.

## 3. What comes back

`ollamaApiResponse` implements the shared `inferResponse` seam.

| Mapping `source` | Reads |
|---|---|
| `response` / `raw_response` | `response` for `generate`, `message.content` for `chat` |
| `thinking` | the reasoning text, when `think` is in use |
| `envelope` | **Ollama's envelope**: `eval_count`, `prompt_eval_count`, `total_duration`, `model`… |
| `model_name` | `model` |

**`source: envelope` does not port to vLLM.** Its counts are `usage.completion_tokens` and
`usage.prompt_tokens`, and a mapping copied across without changing the `path` resolves to
nothing and silently leaves the column alone — [the inference operators page, §2.5](/docs/developer/compute-pipes/operators/infer/#25-response-mapping).

**Ollama reports some failures with a 200**, the way it does for an unknown model. The
backend catches that before the mappings run so the message names the cause rather than a
missing path.

## 4. Build-time validation — this backend's share

The shared builder checks the channels, the mappings and the template ([the inference operators page, §2.9](/docs/developer/compute-pipes/operators/infer/#29-build-time-validation)).
This backend adds:

| Configuration | Error |
|---|---|
| no `model` | `ollama_config must specify the model` |
| `api` other than `generate` / `chat` | `unknown ollama_config api '…', expecting 'generate' or 'chat'` |
| no server URL from any of the three sources | build fails naming both configuration routes |

## 5. Deployment note

`JETS_INFER_URL` was once set only on the UI container. Compute Pipes runs in ECS tasks and
Lambdas, which never saw it, so the operator would have required an explicit `server.url` in
every config. `build_elb.go` sets it on the components that execute the operators too —
`CpipesContainerDef`, `CpipesNodeLambda`, and `CpipesNativeNodeLambda` when cpipes native is
deployed — inside the existing `DoBuildInferServer()` guard.

**That variable names the Ollama infer service**, which is correct for this backend and for
`embed`, and wrong for vLLM.

## 6. Example

```json
{
  "type": "ollama",
  "ollama_config": {
    "model": "granite4.1:3b",
    "prompt_template_name": "classify_claim",
    "keep_alive": "30m",
    "options": { "temperature": 0, "seed": 42 },
    "pool_size": 4,
    "request_timeout_sec": 90,
    "row_key_column": "claim_id",
    "output_mapping": [
      { "column": "claim_category",   "path": "category" },
      { "column": "claim_confidence", "path": "confidence", "as_rdf_type": "double" },
      { "column": "infer_tokens",     "source": "envelope", "path": "eval_count", "as_rdf_type": "int" }
    ],
    "error_channel": { "name": "process_errors.out", "channel_spec_name": "process_errors" }
  },
  "output_channel": { "name": "claims.out", "channel_spec_name": "claims" }
}
```

The input channel and `claims.out` must both name `channel_spec_name: "claims"` — that shared
spec is what makes the in-place augmentation legal ([the inference operators page, §2.1](/docs/developer/compute-pipes/operators/infer/#21-what-the-operator-does)).

**Written as `type: infer` with `backend: "$INFER_BACKEND"`, this same step runs on either
server.**

## 7. Deliberately not built

- **Embeddings (`/api/embed`).** Its output is a vector rather than a set of columns.
  *This was built, as the `embed` operator, on the same seam — the judgement that it wanted a
  different operator held.*
- The prompt-hash response cache and per-prompt batching are shared concerns and are recorded
  in the [the inference operators page, §2.11](/docs/developer/compute-pipes/operators/infer/#211-deliberately-not-built).
